## 2. 数据结构选型（T1.1）

### 2.1 轨道 · 双向链表（D2-A，自实现 `DoublyLinkedTrack`）

祖玛的核心操作序列是："**定位 → 插入一球 → 删除一段连续球 → 拼接 →
连锁继续**"。各候选的逐操作复杂度：

| 操作 | 双向链表 | 单向链表 | 顺序表 |
| --- | --- | --- | --- |
| 插入一球（已定位） | **O(1)** | O(1)（需前驱才 O(1)） | O(n) 搬移 |
| 删除一段 k 球（已定位两端） | **O(k)** | O(k)（找段左端需回溯前驱 O(n)） | O(n) 整体搬移 |
| 消除后两段拼接 | **O(1)** 改 2 个指针 | O(1)（同需前驱） | O(n) |
| 连锁沿拼缝向两侧扩展 | **O(1)**/步（prev/next 双向） | 只能单向走 | O(1) 下标但删除代价大 |
| 定位（下标 → 节点） | O(min(pos, n-pos)) 两端走近 | O(pos) | **O(1)** |

- **单向链表差在前驱回溯**：删除段后连锁检查的是"拼缝左侧末球"，需从
  段右端往回走或另存前驱——逻辑绕且易错；双向指针一步到位。
- **顺序表的 O(1) 定位优势在祖玛中不关键**：指令已给出插入下标，但
  随后的段删除与整体搬移把它 O(n) 拿了回去；连锁每轮都要删段搬移，
  最坏 O(n²)。链表的局部查段与删除总计 O(n)，但本实现的事件定位与完整快照另计，见 §3.1。
- 无哨兵：祖玛轨道**两端高频变化**（首尾插入、删到端点），哨兵对端点
  判断的简化收益低于维护成本；`head_/tail_` 直接指端点，`insert_at` /
  `erase_run` / `reverse_range` 三处端点分支各 2~3 行，可枚举测试覆盖。
- 尾指针使尾插 O(1)（`SHOOT n` 是最常用操作之一）。

### 2.2 待发射队列 · 环形缓冲（D3-C，自实现模板类 `RingQueue<T>`）

语义参照 Baseline `CircularQueue`（固定容量 + front/back + full），但
不复用的原因（接口语义分歧）：

- `take()` 合并 `front()+pop()`——"取球即发射"是本项目每步都要做的原子动作；
- `swap_front_two()`（SWAP 道具）与 `unshift()`（UNDO 放回队首）是祖玛
  专属操作，给 Baseline 的通用队列加这些口子破坏其语义完整性；
- `snapshot()` 非破坏性导出，渲染层用。

环形缓冲 vs 链队列：待发射队列**只在队尾入、队首出、偶尔换头两个**，
固定容量下环形数组最省内存且无逐节点分配开销；撤销的 `unshift` 是
O(1) 逆推下标。模板化是沿用 Baseline 的设计语言（`T = Ball`）。

### 2.3 撤销栈 · 项目内 `LinkedStack<T>`

最终提交版使用 `src/core/linked_stack.hpp` 中自实现的单向链式栈。
头节点为栈顶，`push/top/pop/empty` 支持命令模式撤销，不预设容量上限。
模板定义完整放在头文件，直接实例化 `LinkedStack<UndoEntry>`，无需外部
源码或显式实例化单元。禁止复制，防止节点重复所有权；析构循环释放节点，
避免撤销深度较大时递归析构耗尽调用栈。

链接操作为 O(1)；按值压入 `UndoEntry` 时，还须计入其中变长记录的复制
成本 O(k)，不能把包含复制的完整 push 简写为 O(1)。`make stacktest`
覆盖空栈、LIFO、移动值、复制失败后的状态与十万节点析构。
早期复用实验仅作为历史说明，见 [实验报告.pdf](../实验报告.pdf) 的人机协作过程章节；最终实现不依赖历史源码。

## 3. 消除与连锁算法（T1.4）

### 3.1 核心不变量与主循环

消除的正确性锚在不变量 **U2：轨道上任意时刻不存在 ≥3 连同色段**。
装载时消除既有段（U2'），此后每次插入/反转后运行 `settleFrom`，把
轨道带回 U2。因此"何时检查消除"只有一个答案：**任何改变轨道的操作
之后**，而检查本身是局部化的——只需从**变更点**出发，无需全轨扫描。

```text
settleFrom(probe):
    round = 0
    loop:
        round += 1
        找 probe 所在同色段 [L..R]            # 沿 prev/next 向两侧走
        if 段长 < 3: break                    # 稳定，U2 已恢复
        删除 [L..R]，记录事件与撤销区间
        probe = 拼缝右侧首节点                 # null = 删到尾，结束
```

复杂度需要区分链操作与完整事件生成。令 n 为本步最大轨道长度、d 为
本步删除球数、r 为消除轮数、L 为反转区间长度：

| 工作 | 时间 | 额外存储 |
| --- | --- | --- |
| 已定位后的局部查段/删除/拼接 | O(d+r) | 撤销被删记录 O(d+r) |
| 完整消除操作（含初始定位、每轮 index_of 与 trackAfter） | O(n+d+rn) | 完整事件 O(d+rn) |
| SHOOT 撤销（r 段分别 at(left) 定位回填，再定位删除发射球） | O(d+(r+1)n) | 临时/记录副本 O(d+r) |
| REVERSE 撤销 | O(d+(r+1)n+L) | O(d+r)，JS 反转另需 O(L) |
| 单独区间反转（含下标定位） | O(n+L) | C++ O(1)，JS O(L) |

r=O(n) 时完整消除及最坏撤销可达 O(n²)，不能写成整步 O(n)。
每轮协议要求输出完整剩余轨道，快照文本本身最坏就有 O(rn) 字符。
JS 每轮还保留节点快照，Controller 历史另保存轨道与队列前后快照；
连续 m 次操作至少另有 O(m(n+q)) 的历史数据，事件快照规模需再叠加。
这些是成本上界，不表示每个局面都会达到上界；实测见
[优化验证.md](优化验证.md) 和 [scale-observation.json](scale-observation.json)。

### 3.2 连锁的"拼缝 probe"技巧

删除段 `[L..R]` 后，新的可能消除点**只可能在拼缝**：`L 的前驱`与
`R 的后继`现在相邻。取 `probe = R 的后继`（右段首球）即可——
`findColorRun` 从 probe 向两侧扩展天然覆盖"左段末 + 右段首"的合并段。
删到尾时 `probe = null` 终止。**不需要任何全轨重扫**：这是 U2 保证的
局部性——拼缝以外的段都是消除前的合法段（< 3 或已被前一轮处理）。

README 示例（`R R B B B R R` 装载）走一遍：

```text
装载 → 段扫描发现 BBB（≥3）→ 删除 → 拼缝 R R | R R 相邻 →
probe = 右段首 R → 段 RRRR（4 连）→ 删除 → 拼缝两侧皆空 → 终止。
轨道空 → WIN。
```

### 3.3 炸弹球（首轮特例）

炸弹不参与同色匹配，语义为"消除以炸弹为中心的至多 3 连球"。实现上
是 `settleFrom` 首轮的特例分支：从炸弹节点先右后左扩展至段长 3
（两侧不足时消到端点，最少消炸弹自身）。**炸弹只在首轮生效**——
连锁轮的 probe 是拼缝右侧的普通球。炸弹消除后的拼缝连锁按普通规则
（≥3 同色）。评分与普通消除一致（消除球数 × 倍率）。

### 3.4 变色球

`?` 在 `shoot(pos, color)` 内**落位前**定色为 COLORS 内字母，之后
与普通球无异。撤销时队首放回的是原 `?` 符号（`UndoEntry.shotBall`
记录发射时的原始球）。

### 3.5 REVERSE 的两拼缝

反转 `[i, j]` 后可能消除的点至多两处拼缝：`i-1/i` 交界与 `j/j+1`
交界。对两处分别 `settleFrom`（以交界右侧节点为 probe）。两 probe
落在同一段且已被删除时跳过第二次检查；两条独立连锁各自从 round=1 计分。

## 4. 游戏状态与胜负（状态机）

```text
PLAYING ──轨道清空──→ WIN
        ──队列空且轨道非空──→ LOSE
        ──步数达 LIMIT──→ LOSE
        ──QUIT 指令──→ QUIT
WIN/LOSE ──UNDO──→ PLAYING（有撤销记录时）
QUIT ──协议结束（后续输入不再执行）
```

`refreshStatus()` 在每次操作后重判；WIN 优先于 LOSE（压线一步恰好
清空判胜）。状态只由（轨道空?，队列空?，moves ≥ limit?）三个谓词
派生，无冗余存储——不可能出现状态不一致。

## 5. 撤销 · 命令模式（T1.5，实现中最难的部分）

### 5.1 记录结构

每条 `UndoEntry` 记录：

```text
op           操作类型（SHOOT/SWAP/REVERSE）
pos/extra    操作参数（插入下标 / 反转区间 [i,j] / SWAP 无）
shotBall     SHOOT 发射的球（原始符号，含 ?/*）
removed[]    每轮消除段：{left（该轮消除前轨道中的左下标）, balls}
scoreBefore / movesBefore    该步前的分数与步数
```

### 5.2 多区间逆序回填（连锁撤销的核心）

一次 SHOOT 可能引发多轮连锁，**每轮的区间下标基于当时的轨道状态**
（第 2 轮的坐标在第 1 轮删除后才有意义）。用单一"消除区间"无法表示。

撤销算法：

```text
for k = removed.size()-1 … 0:            # 逆序！
    在当前轨道下标 removed[k].left 处插入 removed[k].balls 串
if SHOOT: 删除下标 pos 处的球（发射的那颗，若未参与消除）
          queue.unshift(shotBall)
if REVERSE: 反转回区间 [pos, extra]
```

**逆序正确性归纳**：设共 n 轮。第 n 轮（最后发生）的区间基于
"前 n-1 轮都已完成"的轨道——它就是当前轨道（撤销开始时）。回填第
n 轮后，轨道状态 = 第 n 轮消除前 = 第 n-1 轮消除后。此时第 n-1 轮
的 `left` 坐标重新有效。依此类推，每次回填恰使下一个（更早的）区间
坐标对齐。回填完第 1 轮后，轨道恢复为"插入发射球后、消除开始前"
的状态；再删掉发射球即回到 SHOOT 前。

REVERSE 的消除回填同理，回填后轨道 = 反转后状态，再反转同一区间
恢复原序（反转自反）。

### 5.3 "删除发射球"的位置正确性

发射球若**未参与消除**：它自插入起就不在任何被消段内，而各回填段的
下标 `left` 均 ≥ 它右侧的某处或整段在其左侧（消除只发生在插入点
邻近，见 §3.1 的局部性）——回填不会移动它，最终它恰在下标 `pos` 处。

发射球若**参与了消除**（同色段含它 / 炸弹邻域含它）：它已被记入某轮
`removed.balls` 并随回填恢复到段中，此时下标 `pos` 处是回填后的同色
球。两种情形统一处理为"删除下标 `pos` 处的球"**结果等价**：前者删掉
的正是发射球；后者删掉的是回填后 `pos` 处的球，而发射球已随段恢复，
`pos` 处这颗与"未插入发射球"状态仅差一球——正是要删的那颗。此
等价性由 §7 的 10⁵ 次随机差分测试验证（撤销到底 → 精确恢复初始状态）。

## 6. 道具功能（T2.5 计划，D4 全选）

| 道具 | 指令 | core 接口 | 数据结构要点 |
| --- | --- | --- | --- |
| 炸弹球 | 队列含 `*`，`SHOOT p` | settleFrom 首轮特例（§3.3） | 无额外结构 |
| 变色球 | 队列含 `?`，`SHOOT p c` | shoot 的定色参数 | UndoEntry.shotBall 记原符号 |
| 交换 | `SWAP` | RingQueue::swap_front_two | 环形数组 O(1) 交换 |
| 提示 | `HINT` | Game::hint（纯查询） | 副本轨道模拟 n+1 个位置 |
| 倒退 | `REVERSE i j` | track.reverse_range + 两拼缝 settle | 内部逆置 O(L)，含定位 O(n+L) |

HINT 复杂度 O(n²)（n+1 个位置 × O(n) 副本构造），n ≤ 10³ 上限下
只有 O(n²) 量级估算，不能据此断言实际操作步数或耗时；报告可讨论"维护辅助计数结构可降到
O(n) 但复杂度换常数不划算"的取舍。

## 7. 已验证内容与阶段 1 发现的缺陷（随机差分测试）

**单元场景自测**（`./tools/selftest` 27 场景，全部通过，ASan/UBSan 零报告）：
装载消除、README 示例归空、单消除计分、两级连锁、不足三连、
连锁完整撤销（含 WIN 回退、分数/步数/队列回滚、重放确定性）、
炸弹（中位/端点）、变色（定色消除、未定色异常）、SWAP 及撤销、
REVERSE 消除及撤销、HINT、LOSE 回退、LIMIT 判负、越界发射异常、
深连锁（RRBBRRBBRR）、连续两步撤销、变色/炸弹撤销。

**随机差分测试**（10⁵ 局，`RGB` 三色、轨道 3~8 球、队列 2~5 球
含 10% 特殊球、每局随机 0~6 步 SHOOT/SWAP/REVERSE、撤销到底）：
撤销后必须精确恢复初始（轨道、队列、分数、步数全等）。通过。

差分测试抓到一个 **20 场景单测未覆盖的真缺陷**（修复留档）：

- **REVERSE 双拼缝 probe 的悬垂指针与越界**：反转后对两处拼缝分别
  settle，原实现两处都按**下标**取 probe（`at(i)`、`at(i-1)`）。第一个
  settle 的连锁消除可能把轨道删短/删空，第二个 `at()` 越界；且即使
  改为先取指针，第一个 settle 也可能把 probeB 所在段删掉，此时对
  已释放节点解引用是 use-after-free（ASan 确认）。
  **修复**：两处 probe 在删除发生前以**节点指针**取出；第二次调用前
  用 `nodeAlive()`（仅比较指针值，不解引用）校验幸存，被删则跳过——
  被删段正是第一次 settle 的消除对象，语义已覆盖。这正是链表"删除后
  其他节点指针不变"优势的反面教材：**指向已删节点的指针**是唯一失效
  形态，必须显式防。注：当时取 `probeB = probeA->prev`，实际仍落在
  左拼缝；右拼缝遗漏由 2026-10-28 的随机差分补强发现，见下节。

- 反向教训（写进报告）：20 场景手写单测全绿 ≠ 正确。上述缺陷在
  "消除恰好删空轨道 + 第二拼缝 probe 越界"的窄条件下才触发，单测
  场景的选取天然偏向"直觉可推演"的局面。随机差分测试补上了这个
  盲区，且顺带验证了 §5.3 等价性论证（10⁵ 局无一失败）。

### 2026-10-28 补强（阶段 6）：计分上限与随机差分入库

- **计分溢出修复**：`ElimEvent.points`、`score_`、`scoreBefore` 及
  `elimPoints` 中间量统一为 `std::int64_t`；每轮得分与总分累加饱和于
  `kScoreCap = 2^53 − 1`（JS `Number.MAX_SAFE_INTEGER`）。JS 引擎以
  相同的 `satMul/satAdd/elimPoints` 实现，双端逐字节一致。
- **随机差分正式入库**：[tools/random_diff.cpp](../tools/random_diff.cpp)
  固定种子 20251020、默认 10⁵ 局（`make difftest`，`DIFF_N=` 可缩短），
  断言 U2、非法操作零副作用、分数增量 = 事件和、全量撤销还原、重放
  确定性。10⁵ 局通过。
- **右拼缝缺陷与修复**：新增 U2 断言后，工具立即抓到上述 REVERSE 修复
  的遗漏——`probeA = at(i)` 与 `probeB = probeA->prev` 同处左拼缝，
  `j/j+1` 右拼缝成三连时不会消除。修复为 `probeB = at(j)`（C++ 与 JS
  同步）；回归用例见 core 自测场景 12b 与 `web_engine_test.js`。
- **场景数**：core 自测 20 → 25（新增 34/60 轮深连锁、WIN 后 swap 守卫、
  右拼缝反转），JS 单测 18 → 22。

**阶段 1 产出**：本文档 + [PROTOCOL.md](PROTOCOL.md) + core 层完整实现
（track/waiting_queue/game + 复用实例化单元）+ 20 场景自测驱动
（main.cpp）。**注意**：阶段 1 的实现已顺带完成了 T2.1–T2.5 的大部分
（core 接口全部落地且经测试），阶段 2 的工作重心因此转为 driver
（指令解析/输出协议）与 CLI 渲染层——即 T1.2 分层中唯一缺失的一层。

**后记（2026-10-20 网页需求新增后）**：最终呈现形式升级为网页可视化
（网页实现阶段），CLI 通道降级为测试/提交专用。core 无 IO 依赖的
分层决策因此变得更有价值：网页（D7=A 的 JS 引擎或 D7=B 的 WASM）
以本文档与 PROTOCOL.md 的语义为唯一规范，与 C++ 实现交叉验证。
