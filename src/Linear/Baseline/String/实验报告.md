### 2. baseline1：字符串的基本实现

**任务要求**：基于动态数组实现字符串类，完成长度、拼接、求子串，并参照 `std::string` 增加至少 5 个功能；与 `std::string` 做性能对比，分析扩容策略对连续拼接的影响。

**数据布局**：`data_` 指向连续堆内存，保存 `len_` 个字符并以 `'\0'` 结尾；`cap_` 是字符槽位总数（含结尾 `'\0'`），恒有 `cap_ >= len_ + 1`。三者与 `growthFactor_`、`reallocCount_` 一起构成类的私有状态。

**扩容与均摊复杂度**：容量不足时按 `growthFactor_`（默认 2.0）扩容。单次扩容 $O(n)$，但容量按等比增长，从 1 扩到 n 的总搬移量为

$$
1 + 2 + 4 + \dots + \frac{n}{2} < n = \Theta(n),
$$

平摊到 n 次追加为 $O(1)$。若每次只扩到刚好够用（`setGrowthFactor(0)`，即 `+1`），总搬移量为 $\Theta(n^2)$——这正是实验要对比的两种策略。

**关键取舍**：

- **RAII 与深拷贝**：析构释放、拷贝构造 / 赋值深拷贝（先分配后释放旧内存，自赋值安全）、移动构造 / 赋值置空源对象，避免浅拷贝的 double free。
- **`substr` 边界沿用骨架语义**：非空串 `pos >= length()` 判越界并抛 `std::out_of_range`（即使 `len == 0`）；`pos + n` 越过末尾时截断；空串任意 `pos` 返回空串。这一语义在实现前并不显然，单元测试最初按“`pos == length` 返回空串”编写而失败，最终统一为骨架语义并由 case02 / case03 锁定。
- **扩展接口 15 组**：`find` / `rfind` / `replace` / `compare` / `insert` / `erase` / `clear` / `empty` / `reserve` / `c_str` / `operator[]` / 比较运算符 / `operator+` / `operator+=` / `size` / `capacity` 等，语义尽量对齐 `std::string`；`replace` 按课程样例理解为“替换首次出现的子串”。
- **为实验暴露观测接口**：`setGrowthFactor` 与 `reallocationCount` 只服务于扩容策略实验，不进入日常接口语义。

### 3. baseline2：模式匹配三步递进

**任务要求**：Step 1 构造极端用例分析朴素算法；Step 2 实现 KMP 并与朴素对比；Step 3 实现 `nextval` 优化并观察常数级提升。功能输出后必须追加可量化的 `PERF` 统计。

**三步算法**：

| 步骤 | 算法 | 关键点 | 时间 |
| :--- | :--- | :--- | :--- |
| 1 | `naiveMatch` | 每个起点逐字符比较，失配后主串指针回退 | $O(nm)$ |
| 2 | `kmpMatch` | 前缀函数 `next`，主串指针不回退，扫描用 `next[matched-1]` | $O(n+m)$ |
| 3 | `kmpNextValMatch` | 跳过“回退后字符仍相同”的无效比较 | $O(n+m)$，常数更小 |

**`nextval` 与课程样例的冲突及解决**：课程骨架的 `next` 采用前缀函数约定，官方样例要求 `AAAAB` 的 `NEXTVAL` 为 `0 0 0 0 0`。按教材式的“相同则继承”递推——令 `k = next[j]`，当 `k > 0` 且 `P[j] == P[k]` 时取 `nextval[j] = nextval[k-1]`，否则取 `nextval[j] = k`——确实得到 `0 0 0 0 0`，但它**不能直接驱动扫描**：失配时跳到与当前字符相同的 `P[j]`，会再次失配，相当于多跳一步，导致漏匹配。为同时满足“输出样例数组”和“匹配正确”，实现提供两张表：

- `getNextVal`：课程样例口径，仅用于 `NEXTVAL` 输出；
- `getNextValFallback`：扫描安全形式，从 `k = next[j-1]` 出发，若 `P[j] == P[k]` 则沿 `next[k-1]` 继续回退，直到不同或 `k == 0`；`AAAAB` 上为 `0 0 0 0 3`。

单元测试逐项断言两表取值，并用独立的暴力实现 `referenceMatch` 对 17 组主串 / 模式串交叉验证三算法结果一致。这一取舍是本 Baseline 最重要的设计决策，也说明“复现样例输出”与“算法正确性”不能混为一谈。

**性能统计口径**：三算法均统计**字符比较次数**。比较次数不受机器与优化影响，能直接反映 $O(nm)$ 与 $O(n+m)$ 的差异；耗时作为辅助证据。

### 4. baseline3：双链 DNA 目标蛋白编码片段检索

**任务要求**：对正向链与反向互补链各 3 个阅读框（共 6 条）翻译，用高效算法（KMP）查找目标蛋白，输出前缀函数 `pi`；把匹配映射回原 DNA 的 1-based 区间；用前缀和快速回答 $q$ 个“完整包含多少片段”的查询，总体 $O(n+m+q)$。

**翻译与匹配**：标准遗传密码表用静态 `unordered_map` 保存 64 个密码子，终止子翻译为 `'*'`，非法密码子为 `'X'`。每条翻译序列上运行自实现 KMP，命中后令 `matched = pi[matched-1]` 继续扫描以支持**重叠匹配**。

**坐标映射推导**：设原 DNA 长度 $n$、蛋白长度 $m$、块长 $3m$，翻译序列第 $a$ 个氨基酸（0-based）在本链上的 0-based 起点为

$$
\mathrm{start} = f + 3a,\qquad f \in \{0,1,2\}.
$$

- 正向链：片段在原序列上占 $[\mathrm{start},\ \mathrm{start}+3m-1]$（0-based），转 1-based 得

$$
L = f + 3a + 1,\qquad R = f + 3a + 3m.
$$

- 反向互补链：`rc[k]` 对应原序列下标 $n-1-k$，片段 `[start, start+3m-1]` 对应原序列 0-based 区间 $[n-\mathrm{start}-3m,\ n-\mathrm{start}-1]$，转 1-based 得

$$
L = n - \mathrm{start} - 3m + 1,\qquad R = n - \mathrm{start}.
$$

**易错点**：反向链必须把**两个端点都翻转**，只翻起点会得到长度为 $n-\mathrm{start}-L+1 \ne 3m$ 的错误区间。官方样例的三个匹配 `2 7 + 2`（正向 frame 1，start=1）、`11 16 - 2`（rc frame 1，start=7，$L=23-13+1=11$，$R=23-7=16$）、`18 23 + 3`（正向 frame 2，start=17）全部吻合，`pi = 0 0`。

**前缀和查询**：所有匹配长度恒为 $3m$，故 $R \le r \iff L \le r-3m+1$。令 $\mathrm{prefix}[x]$ 为左端点 $L \le x$ 的匹配数，则查询 $[l,r]$ 的答案为

$$
\mathrm{prefix}\big[\min(r-3m+1,\ n)\big] - \mathrm{prefix}[l-1],
$$

端点先夹取到 $[1,n]$；区间容不下片段时差值自然为 0。预处理 $O(n+K)$、单次查询 $O(1)$，总计 $O(n+m+q)$，其中 $K$ 为匹配数。

**排序**：按 $L$ 升序，$L$ 相同按 `strand`（`'+'` 在前），再按 `frame` 升序，保证输出稳定且与样例一致。

### 5. 三个 Baseline 的关系

三个 Baseline 相互独立、各自自包含，不共享源文件；共同的工程约定是 `dsaac` 命名空间、`.hpp` 声明 + `.cpp` 实现、`START/END` 标注、中文注释、`test` 自动比对与 `Makefile` 目标命名。算法层面呈递进关系：baseline1 的连续存储是字符串的基础；baseline2 的 KMP 是 baseline3 在 6 条翻译序列上检索的核心工具；baseline3 再把单次匹配扩展为“多阅读框 + 坐标映射 + 批量查询”。

### (2) 审查、测试与优化过程

实现过程中通过单元断言、样例比对、ASan、独立 oracle 与“官方样例锚点”发现并修正了以下问题：

| # | 问题 | 发现方式 | 修正 |
| :--- | :--- | :--- | :--- |
| 1 | `substr(pos == length, 0)` 的语义不确定，单元测试按“返回空串”编写后抛出 `std::out_of_range` | `make unit` 崩溃 | 统一为骨架语义：非空串 `pos >= length` 判越界；测试改为断言抛异常，并测试 `substr(length-1, 0)` 的空串 |
| 2 | 自替换用例 `"aa".replace("a", "aa")` 期望写成了 `"aaaa"` | 单元断言失败 | 首次替换结果为 `"aaa"`（`"aa"` 中首个 `"a"` 换成 `"aa"`），修正期望并在 README 写明“只替换首次” |
| 3 | baseline1 性能程序每次 `append(MyString("x"))`，临时对象带来一次堆分配，使 `MyString` 被严重低估 | 对照 `std::string` 数据异常（21.98 ms vs 3.58 ms），检查基准代码 | 改为 `append("x")`，同为无临时分配路径；百万次拼接降至 7.89 ms，std 3.55 ms |
| 4 | `test` 内嵌 PERF 在未优化构建下测得 `std::string` 反而更慢（8~13 ms / 10 万次） | 与 `make bench` 数据矛盾 | `test` 与 bench 统一加 `-O2`；说明内嵌 PERF 只作格式快照，权威数据以 bench 为准 |
| 5 | `MyString` 与 `std::string` 仍有约 2.2 倍差距 | 类比 List 的“内联”经验，用 `-O2 -flto` 复测 | LTO 下 `MyString` 2.95 ms 反超 `std::string` 3.55 ms，确认差距来自跨编译单元调用未内联，而非算法 |
| 6 | baseline2 的 `getNextVal` 按官方样例得到 `0 0 0 0 0`，但直接用于扫描会漏匹配 | 手推 `AAAAB` 失配路径 + 单元对照 | 拆成“样例口径 `getNextVal`”与“扫描安全 `getNextValFallback`”，匹配使用后者，两表均加断言 |
| 7 | baseline2 单元中 fallback 表的合法性检查从 `i=0` 开始，`fb[0] < 0` 永不成立 | `make unit` 失败 | 循环从 `i=1` 开始，只校验可回退位置 |
| 8 | baseline2 样例 case04 的输入格式写错（第二行误写成 `4`） | `make check` 输出异常 | 重写为 `A / AA / 4 / NEXT / NAIVE / KMP / KMP_NEXTVAL` |
| 9 | nextval 基准规模 20 万时耗时仅 2~3 ms，计时噪声大，甚至出现“比较次数少但更慢” | 对比 `comparisons` 与 `time_ms` 不自洽 | 主串扩到 200 万（2000 个块），比较次数 3 997 000 vs 2 001 998，耗时 7.55 ms vs 3.03 ms，比值同为 0.50 |
| 10 | baseline3 单元把 `translateFrame("ATGATG", 2)` 期望写成 `"M"` | 单元断言失败 | frame 2 从下标 2 起读 `GAT → D`，修正为 `"D"` |
| 11 | baseline3 的坐标映射仅靠手算，缺少独立正确性证据 | 审查时提出 | 编写 `tools/oracle.py`：独立密码表、按定义算 `pi`、逐位置暴力匹配、独立坐标映射，300 轮随机差分全部一致 |
| 12 | 单元程序编译出现 `checkEqInt` 未使用警告 | `make` 输出警告 | 删除未使用的辅助函数，恢复零警告 |

**优化过程的三个体会**：

1. **官方样例是锚点，但不能代替全部正确性**。DNA 样例验证了坐标映射，随机 oracle 才覆盖了反向链、重叠与查询边界；`nextval` 样例则暴露了“样例输出”与“算法可用”之间的冲突。
2. **性能结论必须控制变量**。临时对象、编译优化等级、问题规模任一项不受控，都会得到相反的结论；比较次数这类确定性指标比单次耗时更可靠。
3. **不确定的语义要显式落地**。`substr` 边界、`nextval` 口径、查询越界夹取都写入了 README 与断言，而不是停留在“看起来对”。

## 四、项目总结

本次实验完成了字符串章节的三个 Baseline，共交付 3 个自包含的提交目录、17 组样例、135 项断言与一份可复现的性能 / 正确性验证链。

**主要收获**：

1. **从“能过样例”到“可证明正确”**。官方样例只覆盖有限输入：DNA 任务靠独立暴力 oracle 做 300 轮差分，才把反向链坐标、重叠与查询边界真正验证到位；`nextval` 任务则说明样例数组可能与算法正确性冲突，必须显式区分“报告口径”与“执行口径”。
2. **复杂度要用可观测证据支撑**。`+1` 扩容的二次趋势、朴素匹配的四倍增长、KMP 的线性增长与 nextval 的 0.50 比值，都比单次绝对耗时更有说服力。
3. **性能实验必须控制变量**。临时对象与编译优化等级曾让 benchmark 得出相反结论；LTO 对照实验把“跨编译单元未内联”从猜测变成可复现的证据。
4. **工程惯例降低审查成本**。统一的 `test` 命名、`Makefile` 目标、样例编号、PERF 格式与 README 结构，使三个 Baseline 可以用同一套命令验收。

**不足与改进方向**：

- DNA 任务未对 $n=10^6$、$q=2\times10^5$ 的极限规模压测，复杂度结论为理论上界；可补一组大数据基准，验证实际内存与耗时。
- `MyString` 的 `find` / `rfind` 为朴素 $O(nm)$，未复用 baseline2 的 KMP；若字符串规模很大，可把 KMP 作为 `find` 的可选实现。
- 性能数据为单机单次结果，未固定 CPU 频率或做多进程复现；后续可像 List 报告那样引入多次采样与置信区间。
